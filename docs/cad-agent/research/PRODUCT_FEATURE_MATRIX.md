# Product Feature Matrix

L1 T1, read 2026-11-08 from the reference's public pages only: the homepage (https://mecagent.com/) and the single-page user guide (https://mecagent.com/user-guide). Nothing was observed in the app yet; T5 adds `chain:` cells and T8 upgrades labels from runtime and walkthrough evidence.

Every cell is our own wording. Source quotes are verbatim and kept under 12 words. The label column is CONFIRMED when a public page states the module's core behaviour. Details marked "(unverified)" come from the fetcher's summary of the guide's second half, not from verbatim page text. "Not described" means the public pages say nothing about it.

## Cross-cutting facts

- CAD host: SolidWorks is the only native target, tested on 2024, 2025 and 2026; older versions are not guaranteed. Other CAD systems (Inventor, CATIA V5, NX, Creo, Solid Edge, Fusion 360, Onshape) are listed as coming. Without SolidWorks, users are pointed at Background Tasks with STEP output.
- Platform: a Windows 10 or 11 64-bit desktop app in its own window next to SolidWorks, plus a web app for drawing projects. Mac is not mentioned.
- Stated limits: no release without engineering review, no certification guarantees, no class-A surfacing from vague text, no building from ambiguous instructions without dimensions, and company rules only when supplied.

## Feature traces (T5)

L1 T5, read 2026-11-08. One REA trace_application_feature run per row over the main and preload graph from T3 (run A in `docs/cad-agent/research/ELECTRON_GRAPH.md`), seeded with the channel named in the row's chain cell, both directions. The investigate_feature guided workflow was rendered too; it returns guidance only and pointed to the same trace tool. Raw traces stay in .rea/L1-T5/ (traces-1.json holds rows 1 to 14, traces-2.json holds row 15). Chain hops read left to right: UI, then IPC, then the main handler, then the sidecar, then SolidWorks.

- **One shared path.** 14 of 15 seeds matched a channel. From every one of them the trace reaches the same subgraph of about 1,208 nodes, the same 30 main-side handlers and 200 terminal paths, all ending at call-path expressions. The preload sends every call through one wrapper and the main process registers handlers through one shared helper, so a static trace cannot tell one feature's path from another's. CONFIRMED.
- **No handler body resolved.** No trace reached a backend path, the WebSocket client or the .NET bridge import, and every trace reported zero native handoffs. The hop from a main handler to the sidecar is therefore UNKNOWN statically; T6 runtime capture is the way to observe it.
- **Seeds match by substring.** The task-creation seed also matched its drawing-task variant, and the confirmation seed also matched its answer and closed channels. CONFIRMED from the matched channel lists.
- **Model selection.** The model seed matched no channel. Its only semantic hit is a call inside the active-part bridge member, which concerns the CAD model, not the language model. UNKNOWN where the model choice travels.
- **UI hops.** Only two page chunks showed bridge-member references in their capped graphs (the drawing group and the knowledge upload). The rest of the UI lives in the renderer root chunk, which T3 could not parse, so most UI hops are UNKNOWN.
- **Sidecar and SolidWorks hops** are mapped from `docs/cad-agent/research/SIDECAR_PROTOCOL.md`, which states that which calls run, and in what order, is UNKNOWN until T6. Those hops stay INFERRED.
